# Эскиз и миниатюры изображения: CPU против шейдера

Консольное приложение `SketchBench` и GUI-демо `SketchVCL` / `SketchFMX`: превращают
изображение в карандашный эскиз и сравнивают время обработки обычным кодом Delphi
на CPU и compute-шейдером, скомпилированным PasToSPIRV, на Vulkan. FMX-демо
дополнительно показывает штатный фильтр FireMonkey `TFilterPencilStroke`.
В обоих GUI-демо есть отдельная операция **Миниатюра (thumbnail)** — уменьшенная
цветная копия исходного изображения, не карандашный эффект.

## Алгоритм

1. Яркость пикселя (Rec. 601, целочисленная).
2. Негатив яркости размывается раздельным треугольным фильтром радиуса 1..32.
3. Режим наложения **color dodge** яркости с размытым негативом даёт эффект карандаша.

Вся арифметика целочисленная. Функции из [`SketchMath.inc`](SketchMath.inc) без изменений
компилируются и Delphi для CPU, и PasToSPIRV для GPU — поэтому результат GPU сверяется
с CPU **побитово** на каждом запуске.

| Файл | Назначение |
|---|---|
| `SketchMath.inc` | Общая математика CPU/GPU |
| `SketchMath.pasm` | Модуль PasToSPIRV, подключающий `.inc` |
| `sketch.pas` | Compute-шейдер: три прохода одного pipeline |
| `SketchCPU.pas` | CPU: 1 поток и все ядра (`TParallel.For`) |
| `ThumbnailCPU.pas`, `ThumbnailMath.inc/.pasm` | Уменьшение с усреднением площади; общая целочисленная математика CPU/GPU |
| `SketchVulkan.pas` | Минимальный хост Vulkan 1.0: буферы, pipeline, timestamps |
| `SketchImage.pas` | Загрузка любых форматов WIC и сохранение PNG; синтетическое тестовое изображение |
| `SketchBench.dpr` | Консольное приложение и бенчмарк |
| `SketchEngine.pas` | Общая часть GUI-демо: методы, замеры, побитовая сверка |
| `SketchVCL.dpr`, `MainVCL.pas/.dfm` | GUI-демо на VCL |
| `SketchFMX.dpr`, `MainFMX.pas/.fmx` | GUI-демо на FMX + штатный `TFilterPencilStroke` |
| `SketchDemo.manifest`, `SketchDemo.rc` | Манифест GUI-демо: темы, per-monitor DPI |

Хост использует сгенерированный `SketchShaderBindings.pas` (`--bindings`): размер
push constants и номера bindings берутся из того же `std430`-описания, что и шейдер,
а `PTS_ValidateLayouts` проверяет layout при запуске.

## Сборка и запуск

Нужны Delphi (Win64), собранный `PasToSPIRV.exe`; для GPU — драйвер Vulkan.

```powershell
.\examples\sketch\build.ps1
.\build\bin\SketchBench.exe                       # синтетика 1280x720, 1920x1080, 3840x2160
.\build\bin\SketchBench.exe photo.jpg --radius 8  # своё изображение
```

Параметры: `--radius N` (1..32, по умолчанию 12), `--sizes 1920x1080,...`,
`--iterations N` (GPU, по умолчанию 20), `--cpu-iterations N` (по умолчанию 3),
`--out DIR`, `--shader FILE`, `--cpu-only`.

Результаты: `source.png`, `sketch_cpu.png`, `sketch_gpu.png` и `benchmark.csv`
в `build\sketch\out`. Код завершения 3 — если результат GPU или параллельного
CPU отличается от однопоточного CPU.

## GUI-демо: VCL и FMX

```powershell
.\build\bin\SketchVCL.exe
.\build\bin\SketchFMX.exe
```

Окно: исходное изображение и эскиз рядом, журнал замеров, в строке состояния —
CPU, GPU и таймер.

- **Открыть…** — файл любого формата WIC; **Тестовое изображение** — синтетика
  1280×720, 1920×1080 или 3840×2160.
- **Радиус** 1..32 и **метод**: CPU в 1 поток, CPU на всех ядрах, GPU через шейдер.
- **Операция**: карандашный эскиз либо цветная миниатюра. Для миниатюры вместо
  радиуса выбирается рамка: 128×128, 256×256, 320×240, 512×512, 1024×1024.
- **Построить** — один запуск и сверка с CPU в 1 поток ("бит-в-бит" или число
  отличающихся пикселей). Для GPU показано и чистое время шейдера.
- **Бенчмарк** — все методы, медиана после прогрева (CPU 3 запуска, GPU 20).
- **Сохранить…** — результат в PNG с реальными размерами, а не снимок preview.

### Миниатюры (thumbnails)

Изображение вписывается в выбранную рамку **без обрезки, растяжения и увеличения**.
Например, 1920×1080 → рамка 256×256 даёт **256×144**. Маленькая картинка остаётся
своего размера. Пропорции сохраняются с точностью до целого пикселя; очень тонкая
сторона ограничена одним пикселем. Preview не увеличивает готовую миниатюру.

CPU (1 поток / все ядра) и шейдер выполняют два прохода **area/box resampling**:
усредняют площадь исходных пикселей, включая их дробное перекрытие с выходными.
В отличие от nearest/bilinear это учитывает все исходные пиксели при сильном
уменьшении. Прозрачность фильтруется в premultiplied alpha, затем переводится
обратно в обычный BGRA для PNG. Каналы усредняются в кодированном пространстве
(не linear-light), с округлением до 8 бит после каждого прохода.
Неизменяемый размер копируется точно, включая невидимые RGB.

Ограничения thumbnail-пути: исходные стороны 1..65535, не больше 64 Mi пикселей.
Это удерживает координаты и суммы в 32-битной арифметике GPU. Полный исходник
передаётся на GPU при каждом запуске; назад копируется только маленький результат.
Поэтому GPU end-to-end включает и цену передачи большой картинки.

В FMX четвёртый метод переключается на штатный **`TBitmap.CreateThumbnail`**.
Замер включает создание bitmap, масштабирование и Map/readback результата;
декодирование, PNG и показ preview не входят. Алгоритм масштабирования определяется
FMX/backend и не обязан совпадать с area-фильтром. Его результат побитово не
сверяется. Остальные три метода сверяются с однопоточным CPU.

Пример замера 1280×720 → 256×144: CPU 1 поток ~6.6 мс, CPU 12 потоков ~1.5 мс,
Vulkan end-to-end ~0.4 мс (шейдер ~0.02 мс), FMX CreateThumbnail ~0.45 мс.
Это разные фильтры, поэтому время FMX не является сравнением идентичных алгоритмов.

В **FMX-демо** есть четвёртый метод — штатный фильтр FireMonkey
`TFilterPencilStroke` (`FMX.Filter.Effects`). Он работает на собственном
GPU-контексте FMX (на Windows обычно `TDX11Context`, показан в строке состояния).
Время меряется тем же `QueryPerformanceCounter`: передача `TBitmap` на вход
(новая текстура) → чтение `Output` (рендер на GPU и копирование результата
в `TBitmap`). Это другой, более простой эффект — инвертированный лапласиан
из 5 выборок. Поэтому его результат не сверяется побитово, а сравнение времени
показывает цену штатного пути FMX, а не тот же алгоритм. Параметр `brushSize`
задаёт смещение выборок в процентах от размера изображения (1..19). Демо
получает его из радиуса: `радиус × 100 / max(ширина, высота)`, не меньше 1.

Самопроверка без участия пользователя (тестовое 1280×720, обе операции, все методы,
короткий бенчмарк, снимок окна):

```powershell
Start-Process .\build\bin\SketchFMX.exe '--selftest', "$PWD\build\sketch\gui" -Wait -PassThru
```

В каталог пишутся `*_result.png`, `*_window.png`, `*_log.txt` (FMX также
`fmx_stock.png`), `*_thumbnail.png` и `fmx_thumbnail_stock.png`.
Код завершения 3 — если GPU или параллельный CPU разошлись
с CPU в 1 поток, 2 — ошибка. `scripts\test.ps1` GUI-демо только компилирует.
Тестовые GUI-сборки лежат отдельно в `build\tests\sketch-gui`, чтобы не мешать
открытым приложениям. `ThumbnailCheck.exe` проверяет CPU по независимому Int64
эталону, включая дробное уменьшение, alpha, крайние размеры и переключение
операций; `--gpu` дополнительно сравнивает с настоящим Vulkan.

## Как измеряется время

- **Все пути:** стандартный высокоточный таймер Windows `QueryPerformanceCounter`.
  Перед замерами — один прогрев; в таблице медиана и минимум.
- **GPU end-to-end:** копирование пикселей в staging-буфер, отправка, три dispatch,
  копирование результата обратно, ожидание fence. То есть время, которое видит приложение.
- **GPU, только шейдер:** Vulkan timestamps между копированиями — чистое время трёх
  проходов на видеокарте. Отдельно показаны копирования host→GPU и GPU→host.
- Не входят: декодирование/кодирование PNG, однократная инициализация Vulkan,
  создание pipeline и буферов (выводятся отдельно).

## Пример результатов

AMD Ryzen 5 7500F (12 логических процессоров), AMD Radeon RX 9070 XT, радиус 12:

| Изображение | CPU 1 поток | CPU 12 потоков | GPU end-to-end | GPU только шейдер |
|---|---:|---:|---:|---:|
| 1280×720 | 32.8 мс | 7.3 мс | 0.79 мс | 0.14 мс |
| 1920×1080 | 74.3 мс | 12.9 мс | 1.75 мс | 0.38 мс |
| 3840×2160 | 300.5 мс | 53.8 мс | 6.05 мс | 0.95 мс |

Во всех случаях результат GPU побитово совпал с CPU.

Штатный `TFilterPencilStroke` в FMX-демо на 1280×720 (brushSize 1, TDX11Context):
11–20 мс (медиана, разброс между запусками) от входного `TBitmap` до выходного.
Сюда входят создание текстуры, рендер и чтение результата с GPU; отдельно
время эффекта FMX не показывает. Для сравнения, PasToSPIRV end-to-end — 0.8–1 мс.

Оговорки: CPU-путь — обычный Delphi-код без SIMD-интринсиков, так что сильно
оптимизированная CPU-реализация сократит разрыв. Цифры зависят от железа, драйвера
и нагрузки системы. На маленьких изображениях GPU end-to-end упирается в накладные
расходы отправки и копирования, и выигрыш исчезает (см. 97×61 в тестовом прогоне).
Это пример и бенчмарк одного фильтра, а не универсальная оценка производительности.
